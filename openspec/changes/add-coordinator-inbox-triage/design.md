# Design

## 1. Current evidence and boundaries

Discovery is pinned to main `1ea2d332d7b3a7fc70970d266f0172d54c9e9dbd`.

The caller owns the transaction. `send_message` returns the actual Message and captures Mattermost notice and wake; its false fourth argument suppresses both. |

There is no existing `canonicalMessage` API or field: that phrase means the actual persisted Message returned by Operations. This proposal introduces no alternative message identity. Existing #122 reminder cadence, caps, owner resolution and bootstrap semantics remain with their owner; triage does not silently repair or reinterpret them.

## 2. Explicit contract, not text classification

Propose an optional, exact-key `triage` object on new `kind=note` message input:

- `version`: integer `1`.
- `category`: one of `status`, `ci`, `conflict`, `next_work`, `needs_judgment`.
- `attention`: `routine` or `captain`; required to make intent explicit.
- `source`: a bounded discriminated canonical reference, or null where allowed. No body copy, user-provided URL, arbitrary metadata or executable command.

The `source.kind` discriminator and exact reference fields are defined in `contracts/message-triage-v1.schema.json`. Metadata is bounded to 4 KiB serialized JSON; IDs/revisions use positive exact integers within the interoperable JSON range, task slugs retain the current 128-character limit, and source keys are exact bounded strings without normalization. Over-limit legacy references stay unsupported/manual rather than being truncated. Shape validation does not establish source authority or currentness.

The normalized six-way class is `captain_addressed` when `attention=captain`; otherwise it is `category`. This is the only precedence rule. For example, category `ci` plus explicit captain attention is counted as captain-addressed, not routine CI. The original category and attention remain visible. The configured coordinator receiving an ordinary fallback does NOT itself imply captain attention. The sentinel `captain` in an existing #122 capture filter is not accepted as a real agent ID or silently converted into triage metadata.

Input fields and read contracts are proposed, not current APIs. Proposed exact reads are `GET /api/v1/messages/:id` and `GET /api/v1/messages/:id/triage`; add documented triage-state filters to existing message listing with the same bounded, filter-bound cursor semantics. New CLI input requires the eventual reserved schema floor and must fail clearly against older servers. CLI flags will map exactly to them. `kind=task_order` keeps its independent authorization and scope checks and cannot acquire new authority through triage. Old note clients stay valid; missing metadata produces an unclassified legacy record in enabled modes. Unknown versions/enums/keys or malformed references are rejected before creating a message. Missing/unavailable canonical evidence for otherwise valid metadata produces a retained blocked disposition, never a guessed class or route.

`source` variants are narrowly typed:

- `task_status`: exact task ID and task-event ID/revision, or null for informational taskless status.
- `cooperation_event`: existing Event ID and source key. CI requires an actual `ci_failure/ci_reminder/ci_digest` producer association; conflict requires the canonical rebase/conflict association. Task, repo and recipient are checked against canonical records.
- `task_assignment`: exact task ID and authorized assignment-event revision for next-work.
- `decision_request`: optional exact existing request ID for judgment; this only links context and never answers it.

Server producers associate their actual Message and source inside the canonical transaction. Where Rebase creates its canonical owner Message before #122 finalizes fallback adoption, prepare explicit typed capture intent first, suppress only the generic coordinator-wake projection, and finalize the association after #122 adopts that same Message but before commit. The transaction must fail if finalization is missing; no externally visible half-classified source or second Message is allowed. A sender-supplied event ID or text marker is only a claim until that association is verified. Clients cannot set server provenance, elected delivery IDs, disposition, policy revision or internal actor flags. Authenticated metadata may ask for judgment/captain attention, but it remains untrusted content and grants no authority to execute instructions. Apply existing write authentication/rate limits and bounded input limits; observe-mode attribution is not upgraded into enforcement by this proposal. Automated source-derived routing requires a trusted server association; missing trusted provenance is visible and blocks that route.

No regex, keyword, mention parser, title matching, sender nickname or LLM participates in normalization. Mattermost `props.kind` is a different taxonomy and cannot be copied into this contract without a verified explicit adapter. Legacy/ambiguous messages stay readable and unresolved; no retrospective guessing from markerless or marked bodies.

## 3. One durable triage record and truthful state

Propose an audited `CoordinatorInboxTriage` resource unique on canonical `message_id` (the database is board-scoped). Persist source Message ID/created_at, original recipient, authenticated provenance, input metadata, normalized class or `unclassified`, policy version, capture mode/config revision, canonical source identity, and intended route reference. There is no copied body or independently editable repository. Derive repository from the canonical task; taskless records retain repo null.

Keep immutable classification/source identity separate from append-only disposition transitions and read-time currentness. States distinguish:

- `recorded`: a validated informational status is retained; no response or native effect was required.
- `route_pending` / `routed`: an existing route is awaiting linkage, or a verified durable destination/source reference is linked. This says nothing about native handling.
- `escalation_pending` / `escalation_queued`: one eligible logical escalation awaits #153, or its exact outbox event is linked. Transport accepted/retrying/dead-letter is a separate projection.
- `blocked`: missing owner/assignment, ambiguous legacy provenance, source mismatch, unavailable transport/currentness/native capability, or a coordinator fallback that still needs manual responsibility.
- `superseded`: the source no longer supports the action before delivery. Retain the original evidence and reason.

Expose separate delivery/currentness/handling fields rather than allowing `routed` to imply read, accepted or handled. A durable inbox destination may be successfully linked while native delivery remains unsupported; that limitation stays visible and fails any retirement criterion requiring prompt acceptance. No system call to `msg read`, no fabricated `read_model/read_harness`, and no received/handled cooperation receipt is permitted. Optional auto-ack is deliberately deferred. A routine-only view may filter on routed disposition, but must keep a prominent unresolved/dead-letter view and unchanged raw unread access.

An immutable triage row cannot be reclassified on replay. A conflicting retry fails visibly. A captain-reviewed correction, if needed later, must retain the old evidence and reuse the same logical escalation key; v1 requires a new explicit message for new intent. Correctness never depends on a numeric message ID implying commit order.

## 4. Deterministic routing matrix

Only direct notes addressed to the exact configured coordinator identity are candidates in v1. Shared comments and other inboxes retain existing behavior. Explicit captain attention is a directive within that coordinator-inbox contract, not an unconfigured separate captain-address directory. Snapshot the selected registered, non-retired coordinator and configuration revision; missing coordinator blocks activation. Configuration rotation does not create new occurrences for old messages.

| Normalized class | Deterministic behavior | Missing or unsafe evidence |
| --- | --- | --- |
| `status` | Record the report and its validated task-event reference. If an existing recipient wake/delivery is relevant, link it; do not send the report back to its author or manufacture a reply/wake. Taskless informational status is retained without repo scope. | An alleged task/source mismatch remains blocked; no task state or heartbeat is changed from message content. |
| `ci` / `conflict` | Adopt the existing producer association and #122 selector result. Worker result links the Event/delivery; inbox result links its exact Message; no second owner resolution, fallback call, forward or worker frame from the inbox consumer. | No owner, coordinator-only fallback, disabled cooperation, missing source proof or unsupported typed currentness remains visible. The coordinator fallback is not successful autonomous handling. |
| `next_work` | Verify the requesting sender is the exact active assignee of the referenced already-authorized assignment, with current task revision/scope and idle predicate. Reference/capture the SAME #156 `idle_assigned` occurrence under its owner; #150/#156 retain admission and native custody. | Missing task, several possible assignments without an exact reference, revoked/changed assignment, unavailable/quota/admission state or unsupported native route remains blocked. Never choose a task from the open queue. |
| `needs_judgment` / `captain_addressed` | Retain one logical #153 escalation keyed to this Message ID, containing only public IDs/links. | Missing transport/subscriber/signing readiness remains pending/blocked and visible; it cannot be treated as delivery. |
| `unclassified` | Preserve legacy inbox access and explicitly unresolved disposition. | Never infer routine status or suppress it as noise. |

All routine normalized classes emit zero coordinator webhook events, including errors. A missing owner does not get silently relabeled judgment. A producer or authorized sender can instead submit an explicit new needs-judgment/captain-addressed message. Classifier policy does not alter #122 escalation cadence or replace its source keys. Multiple messages referring to one existing assignment/source adopt the same underlying wake/delivery; each message retains its own audit, with no new source effect.

Taskless next-work/CI/conflict cannot acquire repository or recipient scope from the sender, enrollment list, working directory or configured default. Taskless judgment/captain messages can produce board-level public-ID/link escalation without a task/repo field.

## 5. Atomicity, election and reconciliation

1. Validate input and select the existing source owner's route in its canonical transaction. CI/conflict producers continue to own #122 selection. Triage never calls that selector from generic inbox consumption or while holding worker/provision custody.
2. Create or adopt the exact Message produced by its existing source owner, then capture typed source association, triage record/audit and any local escalation eligibility in that same transaction. A worker-only Event with no coordinator Message is outside the inbox classifier and produces no triage row. An existing coordinator Message that references an Event retains its own Message-ID identity, but does not become the Event's canonical fallback Message by assertion. An inserted triage record cannot point to a rolled-back message; a newly classified enabled message cannot commit without its initial disposition. Local capture failure rolls back the source operation. Network failures occur later and never roll back committed source data.
3. Ordinary message producers retain existing Mattermost behavior. Introduce an explicit per-projection capture policy rather than reusing `capture_notice? = false` and accidentally suppressing both Mattermost and wake projections. Typed #169 producers preserve their explicit exact-envelope capture before commit.
4. In active mode, routine coordinator notifications that triage has safely recorded/routed and all escalation-eligible messages (pending or queued, including transport-unavailable cases) must not also create an independent generic coordinator `unread_dm` effect. Persist this capture disposition and honor it in initial wake capture, pending reconciliation AND `Wake.Reads.canonical_state`/reservation-time eligibility. Under the canonical Message lock and existing wake-election/CAS order, atomically fence an unreserved generic wake before admitting an alternate escalation channel; a merely stored exclusion cannot leave an old wake reservable. Enqueue must recheck that no reserved/submitting/submitted/accepted/uncertain attempt exists. Preserve such attempts for their owning #156 reconciliation rather than cancelling them, and admit no #153 event while overlap is unresolved. If owner reconciliation proves the old channel accepted/handled the source, record that existing-channel result and do not replay the message into #153; only proven non-submission plus unhandled source permits channel migration. A later owner result of `not_submitted` may return an old intent to pending, but cannot erase this durable exclusion; every subsequent reserve revalidates it. The route transition and outbox enqueue fence must be covered by concurrent reserve-versus-enqueue tests. Legacy, routine blocked and pre-activation work stays visible on its retained path. A newly active explicit escalation owns its channel from local pending capture even when #153 is unavailable; it stays visible to the retained sweep/manual workflow, without creating a generic native coordinator wake. Before changing a previously captured generic wake, inspect its existing reservation/receipt; never cancel or replace accepted/uncertain work to force parity. Such overlap is a cutover blocker.
5. Existing #122 exact-marker adoption remains in its owner; it is not a triage classifier. Require an actual producer association for active routing. Ambiguous legacy marker matches stay manual. An Event return never justifies synthesizing another Message to satisfy typed wake capture.
6. A bounded pending-state repair job finds committed candidates missing linkage, unresolved dependency transitions and eligible #153 enqueue work. Use source existence/transition predicates with uniqueness and retry-safe CAS, not a max-ID watermark. New-capture transactions are primary; this is server consistency repair, not a coordinator LLM inbox poll. No new host schedule is installed by this change.
7. Reconciliation loads immutable candidate references, then enters a fresh owner-ordered transaction and revalidates sources before effect/linkage. Never acquire a canonical task/PR/obligation lock after a triage, outbox, worker or attempt lock. For #169, preserve its base/PR/poll-state prefix; #122 election remains before downstream worker custody. Triage locks its Message/unique row only after required canonical locks. #153 enqueue takes the outbox lock last, without callback into source owners. HTTP/signing delivery and native I/O occur outside database locks. Remote deadlock/race tests must prove the final shared order before active mode.

Same-message concurrent capture resolves through the unique Message-ID triage key and returns the existing immutable result; changed source metadata conflicts. This does not add idempotency to the old message POST: retrying that endpoint today can create another Message ID. Only exact same canonical IDs are deduplicated here; client creation idempotency is a separate API concern. An explicitly repeated message is a distinct occurrence.

## 6. Adapter to #153, with no second transport

This is a proposed integration contract, not a claim that #153 exposes these APIs today. Before integration, its owner must provide a shared transaction-safe enqueue operation accepting a unique producer key, event type, schema version and an allowlisted payload, and return the existing event ID on identical retries. Enqueue is always deferred until after original Message/triage capture commits: source capture retains local escalation eligibility, and a later pending-state repair transaction performs enqueue plus event linkage. A crash between them leaves discoverable pending state. The outbox MUST be in the same database transaction as that triage linkage; if the eventual transport cannot do that, this adapter remains blocked pending an approved consistency design.

- Logical key: tuple `(stable board namespace supplied by #153, coordinator.inbox_attention, canonical Message ID)`. It is independent of policy/config revision, subscriber, signing key, attempt and deployment. Exactly one logical event exists for this key.
- Event envelope: fixed type `coordinator.inbox_attention`, schema version `1`, event ID and the stable idempotency key. Payload allowlist: public `message_id`, `triage_id`, optional `task_id`, and server-generated `message_url`, `triage_url`, optional `task_url`. No body, snippet, title, summary, source key text, model output, identity profile, repository credentials or arbitrary URL. Class/context are retrieved through the canonical read surface.
- Add an exact, non-consuming authenticated message/triage read route as part of this slice; it does not exist today. Generate source links from a configured canonical board HTTPS origin and escaped validated IDs, never Host headers or supplied URL fields. Links contain no bearer tokens, signed login grants, userinfo or credential query parameters. A public identifier does not make source contents public: reads retain the board's actual access controls and never widen them.
- One designated coordinator subscription per board receives this event type. #153 owns authorized endpoint configuration and secret custody; ordinary senders cannot select either. Missing, multiple or unverified destinations block activation. Delivery cannot fall through to arbitrary addresses, public Mattermost posts, email or another agent.
- When #153 is absent/disabled, retain `escalation_pending` with `outbound_transport_unavailable`; no local HMAC sender, HTTP client loop, secret setting or retry queue is added. When ready, a reconciliation transaction enqueues once and links its event ID atomically. Later retries/restarts/config changes reuse that ID.
- #153 owns delivery leases, immutable payload bytes, signature format, bounded retry/backoff policy, attempt logs and dead-letter retention. Integration requires a documented bounded attempts/age policy, non-consuming attempt reads and authorized replay action; unspecified/unbounded retry is a readiness failure. Dead-letter replay keeps the same logical key and consumer dedup identity. It does not mark the message read or manufacture a second event.
- Require the shared transport's signature to bind exact body bytes, delivery timestamp, key ID and event identity, with constant-time verification and bounded freshness checking. The receiver rejects missing/invalid/stale signatures and unrecognized keys before effects. A legitimate later retry has a fresh delivery timestamp/signature but the same logical event ID/key.
- Rotating signing keys supports an explicit verification overlap and revocation boundary under #153. Unknown/revoked keys fail closed; no unsigned downgrade. Rotation neither renumbers events nor erases attempt history. This proposal provisions no key, endpoint, grant or secret.
- HTTP timeout/connection loss is an unknown outcome, so shared transport may retry the SAME event. Retryable failures (including 429 with bounded Retry-After and 5xx) and permanent refusals follow #153's published policy and become observable. Do not follow redirects or send signatures/IDs to an unapproved origin. Transport owns destination/SSRF safeguards including private/loopback/link-local targets and DNS rebinding policy.
- The coordinator consumer durably stores accepted event IDs/keys and a payload hash before acknowledging. Acceptance and enqueue of one coordinator work item are atomic. Duplicate delivery with identical bytes acknowledges the existing item without another invocation; same key/different payload is rejected and audited. Crash before commit causes retry; crash after commit before HTTP acknowledgment safely reuses the existing work item. The work queue itself retains a stable invocation key/uncertainty boundary, so restarting the consumer does not rerun an accepted item blindly.

A signed webhook proves an allowed sender delivered an event, not that its linked message instructions are authorized. The consumer fetches exact source evidence with existing scoped read access and applies its normal judgment/confirmation policy. It never treats webhook acceptance as source handling. Full guarantee is one logical escalation and one durable consumer work item; exactly one physical HTTP request is impossible under at-least-once delivery.

## 7. Failure visibility, compatibility and rollout

Proposed per-board mode is `off` by default, then `shadow`, then `active`. Mode changes and source classification are auditable. Existing cooperation and wake flags remain independent and cannot be enabled by triage.

- Off: preserve current routing, wake, inbox and read behavior. New clients may store valid explicit metadata, but no triage route or outbound event is emitted.
- Shadow: capture classifications and proposed references without forwarding, reservation, webhook enqueue, suppression of existing wakes, or acknowledgement. Compare with the existing sweep; record unsupported paths honestly.
- Active: apply the approved deterministic handlers and #153 adapter only when each route's explicit capability gate passes. Routine messages always have zero escalation events. Missing transport does not prevent the independent local slice shipping, but blocks escalation readiness and sweep retirement.

Mode transitions use an auditable configuration revision. By default, active eligibility covers only new source transactions admitted under that active revision; repair queries filter on that eligibility, not just `message_id > cutoff`. Off/shadow backlog is not silently re-enqueued on upgrade. Any historical activation requires an explicitly approved, bounded exact-Message-ID cohort, with original classification retained and an appended activation disposition using the same logical key. Check legacy generic wakes/outbox events/consumer work before admitting each source; pending accepted or uncertain overlap blocks promotion. Admission/enqueue revalidates current mode/coordinator revision under the documented source-first transaction order, and #153 rechecks its dispatch pause outside the source transaction. A stale mode snapshot cannot authorize new dispatch after a pause.

Expose source ID, normalized class, policy/config revision, audit history, route references, unresolved reason, source currentness, transport attempt/dead-letter status and separate handling state in existing message/task reads plus an exact triage read. Paginate unresolved records before bounded limits; filtering must not starve older/lower-ID late commits. Read/list/watch never acknowledges. Keep message bodies out of metrics/logs/dead letters; store reason codes and public references, with bounded sanitized remote error classes rather than remote response bodies.

Before retiring the sweep on farm01, the captain must review a retained live evidence packet for the exact deployed commit/config and observation interval. It must account for all coordinator messages in that interval, with source IDs and expected/actual dispositions, not only successful examples. It must prove all six classes, taskless and legacy cases, duplicate/restart/response-loss and key-rotation/dead-letter recovery; zero lost/duplicate logical escalations; zero routine coordinator events; known route failures and unsupported native paths cleared or explicitly covered by an approved visible manual workflow. An arbitrary quiet interval or zero-message sample does not establish equivalence. Use bounded synthetic non-secret sources for missing cases in an approved test destination; fixtures alone are not live proof.

The interval and representative traffic requirements belong in the activation review packet, with counts and outstanding exceptions. Record current sweep identity, pending/accepted coordinator work and intended cutover owner. No pending/uncertain duplicate channel may remain. Only then may a separate explicit captain decision authorize pausing the exact inbox-sweep routine. This proposal and its implementation approval do not authorize that pause.

Rollback pauses new #153 dispatch through its existing control and changes triage to shadow/off, preserves all triage/outbox/audit/consumer receipts, reconciles accepted/uncertain work, and restores the previous sweep owner only under the approved operational plan. It does not delete queued events or replay accepted work. A source/delivery correctness regression reopens the cutover gate.

## 8. Implementation slices and validation

A. After proposal approval: additive explicit metadata, audited classification/disposition, canonical-source linking, read-only visibility and off/shadow tests. No transport dependency or live behavior change is required.

B. After the local routing approval and owner seam agreement: integrate the single existing source owners, initial/reconciled wake eligibility and gated active routine routing. Unsupported #169/native paths remain visible, not broadened.

C. Blocked until #153 lands and its contract is verified: atomic enqueue, signed transport/receiver replay proof and end-to-end escalation. Do not implement #153 inside #186.

D. Separate operational authority: actual endpoint/key setup, deployment, activation, equivalence review and sweep retirement. No schema identifier or operational authorization is allocated here.

Remote implementation proof must extend `coop_inbox_fallback_test.py`, `wake_intents_test.py` and packaged API/CLI/real-Postgres coverage. Include atomic rollback, source mutation races, late commit pagination, exact-ID concurrency, #122 source election/adoption/bootstrap behavior, typed metadata mismatch/currentness refusal, initial/reconciled wake suppression parity, authenticated input, no-body payloads, malicious URLs/metadata, and replay-safe receiver crashes. Run repository remote gates only with remote configuration; never use local Bazel as a fallback. Current proposal verification is recorded separately in `verification.md`.
