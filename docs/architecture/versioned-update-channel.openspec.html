Proposal — what changes

Proposal

Why

Agents and operators install Agentboard once, then lose visibility into CLI and workflow changes. A versioned update channel will make drift actionable without interrupting active work, and extend the separate installer/release proposal into a deployment path that needs no repository checkout.

What Changes

  • Publish a bounded, versioned update-manifest.json alongside immutable release assets. Track CLI semver/build identity, independently versioned skills and their canonical content digest, compatibility requirements, checksums, release notes, and an optional complete Compose bundle.
  • Add read-only agentboard update check and agentboard skills outdated, with explicit component results and freshness. Add consent-based update apply and skills upgrade, preserving managed-file ownership, offline skill installation, and existing command exit-code conventions.
  • Add a dedicated Ash domain, audited resources and AshOban observer for release snapshots, opted-in installation reports and durable notification receipts. Expose cached status through the Phoenix API and dashboard; use the board inbox as the durable agent signal and existing Mattermost delivery only when enabled.
  • Package Compose together with every runtime support file, pinned application/database images and a non-secret environment template. Download/stage it explicitly; start services only through the operator's subsequent docker compose up.
  • Split implementation into four cohesive PRs: manifest contract/packaging; local update commands; Ash observer/API/notifications/dashboard; no-clone Compose distribution and onboarding.

This PR is planning only. It does not implement an updater, change authentication, start jobs, install routines, cut releases, merge or deploy. No breaking change to existing board APIs or offline skills install is proposed. Updates never silently replace utilities, restart agents, alter leases, modify third-party skills/hooks, or roll Kubernetes images.

Capabilities

New Capabilities

  • artifact-update-channel: trusted release catalog, independent artifact identities, explicit local update lifecycle, durable drift reporting and bounded notifications, and complete versioned Compose distribution.

Modified Capabilities

None. There are no canonical specs in openspec/specs/ at the inspected baseline. The in-flight add-release-pipeline-and-installer change owns release-pipeline and cli-installer; this change consumes its output without rewriting those capabilities or making #127 depend on #57.

Impact

  • Planning source: GH #57; prerequisite contract: GH #127 and add-release-pipeline-and-installer.
  • Expected implementation areas: .github/workflows/release.yml, scripts/publish-release, build/release/, embedded skills packaging, internal/cli/, internal/client/, new web/lib/agentboard/updates/ resources/domain, runtime queue configuration, Phoenix routes/LiveView, Compose packaging, and generic setup/release docs.
  • Additive PostgreSQL migrations require a schema ordinal allocated against current main at implementation time; this proposal reserves none. CLI board writes remain API-only; no singleton GenServer broker serializes SQL or provider requests.
  • Captain-approved policy (board message 1193, 2026-10-08): GitHub immutable release-attached, version-pinned manifest/assets are authoritative; skills ship separately with semver and the existing canonical bundle digest; captain summary plus opted-in recent agents receive signals, with none for unknown installations. This approves the design policies; runtime implementation remains a separate authorization.
  • Review material: docs/architecture/versioned-update-channel.html and a portable Lavish rendering of this change. Maintainer-specific rollout remains separately authorized work.
Design — contracts, boundaries and recovery

Design

Context

See proposal.md for the user goal. This design follows the captain's three approved policies recorded in policy-review.md and board message 1193. It extends the separately planned #127 release pipeline and installer; neither that change nor its files are modified here.

Observed on main 63c76bc: internal/cli/skills.go installs embedded, rewritten Markdown/reference files into verified content-addressed bundles and changes only owned discovery symlinks. Its digest hashes sorted relative paths and file contents, each followed by a NUL byte. version and release packaging are still pinned to 0.1.0. Compose currently requires build contexts, certificate and initdb files. The Phoenix application already uses pooled Ecto connections, Ash resources/audit, AshOban and PostgreSQL scheduling/receipt records. GitHub provider admission currently depends on the PR-observation flag; reusing that flag as update enablement would couple unrelated features. Agent API tokens have off/observe modes, not enforced authentication.

Goals / Non-Goals

Goals: identify installed and available artifacts independently; offer explicit safe updates; retain drift/freshness and notification state through pod restarts; provide complete release-pinned Compose distribution; give implementing agents concrete contracts and failure proofs.

Non-Goals: automatic upgrades, running downloaded scripts from a manifest, restarting live agents, altering claims/PR follow-up, replacing other tools or skills, installing harness hooks, maintaining a workstation polling singleton, changing auth enforcement, or automating image/deployment rollouts. Mattermost is a gated projection of a board notice, not the notification authority. NATS/Dgraph are unnecessary for this catalog and receipt data.

Decisions

1. Authority, channel resolution and identity

GitHub immutable release assets are the sole authority. A release has its own version-pinned update-manifest.json; the board caches its validated normalized meaning and provenance, never authors a competing manifest. The default stable channel selects the highest eligible SemVer release from complete bounded GitHub release enumeration: published, non-draft, non-prerelease, immutable, with tag/commit and required assets validated. No eligible release means unavailable, not “current”. Explicit --version selects an exact release; preview releases are outside v1 channel support. A moved GitHub “latest” marker cannot downgrade an accepted channel. Pin the repository/API origin in trusted operator configuration; remote content cannot choose another repository.

Manifest v1 is JSON, maximum 256 KiB, duplicate-key rejection, supported major schema only, no unknown executable fields. The release publisher generates it from verified outputs and validates it before publication. generatedAt is informational; database observation time controls freshness. Required fields:

FieldMeaning
schemaVersion, channel, generatedAt1, stable, UTC RFC3339
releaserepository owner/name, numeric release ID, tag, full source commit, version-pinned notes URL
cliSemVer, full build commit, minimum compatible updater version, supported board API range, required board schema floor, four platform assets keyed by OS/architecture
Each CLI assetrelease asset name/ID, HTTPS URL, byte size, archive SHA-256, extracted binary SHA-256; SHA256SUMS agrees
skillsindependent SemVer, canonical bundle digest, minimum installer version, archive asset identity/size/SHA-256, exact bundle layout/format version
composeoptional complete-bundle SemVer, archive asset identity/size/SHA-256, supported engine platforms, minimum Compose version, application/database image references by digest, registry-login prerequisites

SemVer is parsed, never compared lexically. Reusing a published artifact version with changed digest/commit is a conflict. A CLI release can reuse unchanged skills version/digest; changed skill payload requires a version bump. Stable publication cannot silently regress a component. Checksums provide byte integrity under the trusted GitHub/HTTPS release origin, not an independent signature against compromised maintainers or release authority. Require GitHub's immutable-release indicator; publishing a mutable draft is insufficient for enrollment. Do not claim signatures/attestations are verified in v1. GitHub's release API exposes draft/prerelease/immutable status and asset identities; platform fixtures must prove parsing of their actual representation.

A separate remote mirror or OCI skills service adds another authority and delivery lifecycle, so it is excluded by the approved policy. #127 may continue its pre-manifest install path; adding a manifest must not force old releases or installers to fabricate one.

2. Separate skills distribution using the existing ownership contract

Package the post-rewrite installed bundle, including skill-local fragments and referenced API/quota/participation/context/charter files. Use one canonical bundle producer for embedded installation and release archives so release identity matches skillDigest, rather than hashing raw skills/ sources. Archive SHA-256 and canonical tree digest are distinct values and both must match. Metadata is outside the digested payload; the archive contains only declared regular files/directories, no links, devices, absolute paths, traversal, duplicate names, excess entries, or oversized decompressed data. Limits: 8 MiB compressed, 32 MiB extracted, 2,000 files, 128 path segments; fail before writes outside private staging.

skills install remains offline with the embedded bundle. A verified remote skills upgrade stages a new immutable content-addressed bundle, preflights every destination and old bundle, then uses the existing installer lock and per-link atomic replacement. It never overwrites foreign directories/links or edited bundles. Preserve verified prior bundles. A protected local receipt/journal binds version/digest to each selected discovery directory; after interruption it records exactly which owned links advanced. A resumed operation revalidates actual files and completes or restores only matching owned links. Do not promise an atomic switch of all directories: links change individually. No background cleanup removes an old bundle still referenced by any recorded installation.

An older install with no version receipt is unknown unless its verified digest exactly identifies a catalog payload; a receipt cannot override edited actual bytes. New CLI install does not imply installed skills changed. The human or agent must explicitly re-read changed workflows in its current session; discovering new files does not prove refreshed model context or an installed wake loop.

3. Read checks, explicit apply and bounded transports

Proposed interfaces:

CommandEffect
update check [--version V] [--source board|release] --jsonCompare local CLI/skills receipts and actual identities; default board cached view, explicit release reads GitHub when board is unavailable
skills outdated [--dir DIR] --jsonSame catalog comparison for the chosen discovery directory; no installation/report mutation
update apply --component cli|skills --version VExplicit exact-version install; default CLI destination ~/.local/bin/agentboard; never implicitly updates both
skills upgrade --version V --dir DIRExplicit independent skills upgrade through the shared owned-bundle path
update report [--notifications on|off] --jsonExplicit API report/enrollment; off cancels pending future agent notices
update compose fetch --version V --dir DIRVerify and stage a fresh complete Compose directory; does not start or upgrade services

Local checks can read local receipts without an agent ID; board reads use existing transport conventions. --source release needs no board capability and never forwards Agentboard credentials to GitHub. Machine result schema version 1 gives installed/target identities per component, current, update_available, ahead, unknown, incompatible, or conflict, source provenance, observed time, fresh/stale/unavailable, and a next action. “Updates available” is a successful comparison (exit 0), not an error. Existing exit codes remain 2 invalid input/context, 3 missing exact release/asset, 4 ownership/version conflicts, 1 infrastructure/compatibility failure. Stale results can inform the user but do not authorize apply. The board schema floor and API range concern the target CLI; the updater's minimum version is checked separately, and an incompatible board is never auto-migrated.

Apply downloads an exact release manifest anew, validates provenance/compatibility, and shows components, versions, destinations and checksums before consent. Interactive consent comes from the controlling TTY; unattended use needs explicit --confirm, and neither stdin piping nor a read-only check is consent. This updater flag does not authorize No-mistakes gates. Downgrades and ambiguous dev builds refuse in v1. CLI replacement requires a verified managed-install receipt shared with #127, actual current-file fingerprint and a writable safe parent. Foreign/package-manager installations get manual instructions; no sudo or package-manager bypass. Stage beside the destination, verify archive and binary hashes/version on the supported execution platform, fsync as appropriate, recheck destination/receipt under a local lock, then atomic rename. Failure before rename preserves the original. Keep a prior verified binary and receipt; rollback is an explicit local recovery action only when board compatibility permits. A running agent process keeps its already-loaded executable; no harness/session restart is attempted.

All requests have cancellation, capped bytes and deadlines. Initial limits: manifest 256 KiB; CLI archive 64 MiB compressed/128 MiB extracted/8 files; skills above; Compose 8 MiB compressed/32 MiB extracted/2,000 files; 20-second metadata and 120-second download deadlines; at most three redirect hops/retries. Authenticate GitHub metadata only at configured API origin using an operator GitHub credential if configured, never laptop OAuth auto-discovery. Asset redirects are separately allowed only to explicitly configured GitHub download hosts, HTTPS public endpoints, no userinfo/private/loopback/link-local destinations, and no authorization or board identity headers after a host change. Check every redirect and resolved connection destination; an arbitrary manifest URL cannot become an SSRF endpoint. The existing board client rejects redirects and bounds 429 retries; extend via a separate release-download transport rather than relaxing board transport globally. Honor Retry-After and GitHub reset/secondary-limit signals; if delay exceeds the command deadline, return a typed retry time instead of sleeping past it. Errors expose safe status/code, never token/query strings, remote raw bodies or downloaded release notes as executable instructions.

4. Ash domain and replica-safe observer

Add Agentboard.Updates with AshPostgres resources: channel policy/cursor, immutable release snapshots, attributed installation reports, and notification intents/receipts. Meaningful mutations use AshPaperTrail and AshEvents in the transaction; exclude raw manifests and frequent unchanged report/fetch chatter from audit copies. Report identity: local random installation UUID, declared board agent, CLI version/build/binary digest, verified skills version/digest, selected channel and notification consent. No hostname, absolute path, repo inventory, secrets or arbitrary text payload. One agent can have multiple installs; the dashboard shows each, rather than overwriting one seat's facts with another's. Reports are self-reported attribution in off/observe auth mode, not trusted software attestation. Use the current principal-mismatch protections when a verified principal exists; #57 never enables auth enforcement or grants report submission new board privileges.

An independently gated AGENTBOARD_UPDATES_ENABLED=false by default controls a dedicated updates AshOban queue (concurrency 2) and scheduled action. Schedule wakes every minute but PostgreSQL next_poll_at admits one channel fetch per 6 hours with jitter; failures back off up to 24 hours, respecting longer provider retry floors. A short row lock creates a lease + monotonic fence, then commits before network I/O. Success or error is recorded only if the same fence is still current; expired/crashed work is recovered by a later job, and a stale worker cannot replace a newer snapshot. Ordinary SQL and HTTP run in job/request processes through Repo's pool, not a query/poll GenServer. Queue concurrency is a bound, not the ownership lock. A temporary provider outage never makes readiness fail or blocks board/CI work.

Refactor provider admission's enablement input so update observation can use the same PostgreSQL GitHub credential budget/backoff while PR observation remains off. Do not introduce a competing budget for the same token or unpause existing delivery queues. Allocate only short budget locks; no network under transaction. Fetch/cache ETag per exact representation/origin. A validated 304 refreshes the matching cached object's observation time; 304 with no corresponding bytes is incomplete. Malformed/oversized/unsupported manifest, incomplete release enumeration, moved version identity, unauthorized or failed fetch records failure/freshness but preserves last-known-good bytes. Fresh means a fully validated success no more than 24 hours old; older snapshots stay visible as stale. A CLI apply always revalidates the authoritative exact release.

5. Reporting API, dashboard and notices

New proposed routes: GET /api/v1/updates?channel=stable, POST /api/v1/updates/installations/report, GET /api/v1/updates/installations (captain capability), and a captain-protected update-policy mutation route. GET shows validated latest snapshot/provenance/freshness and no raw remote HTML. Reports support a stable idempotency key and monotonically increasing local sequence; same-key different-body conflicts, delayed reports never overwrite a newer install/consent record. Server observation time defines recency. Repeated identical reports refresh liveness without producing repeated audit/notices. Reuse Phoenix compatibility/auth/rate-limit plugs and input error envelopes; reads/writes remain API-only. Allocate new schema floor at implementation time; older servers return schema_unavailable before these writes and never receive a speculative new route request after incompatible meta.

Recent means report seen within 7 days. Only a report explicitly enrolled for notices can generate its agent inbox signal. Missing, incompatible or stale target/installation evidence is “unknown”/“stale”, not drift. Captain summary lists available release, count of current/outdated/unknown/ahead/conflicted opted-in reports, supported components and observation/error times. Agent detail shows rows per install with exact next check/apply action and session re-read guidance. Preserve existing theme tokens, Tailwind v4 and Kanban; this is a settings/agent-detail addition, not a board layout redesign.

Freeze notice intent with recipient, installation, component, target version/digest and generation. Unique database identity yields at most one board inbox notice per recipient/component/target identity across installs, replicas and retries; select a bounded recent-install summary for its body. Recheck consent, recency, target and installed mismatch before committing a new notice. Consent-off cancels unsent intents; it cannot erase an already-delivered message. Produce the inbox message and its delivered receipt in one transaction. New target versions are coalesced while pending, and notices are capped at one summary per recipient/day; do not send daily reminders for an unchanged version. Enrolling/reporting after a release triggers the same reconciler, so late reporters are not missed. Offline old seats get no backlog blast on re-enrollment. Captain visibility is always a dashboard summary, not a DM to every captain identity. An optional configured captain inbox recipient gets the same bounded summary policy.

If existing Mattermost bridge/provisioning is enabled and routing is configured, project the committed notice through its retained outbox and idempotency rules; outage leaves the board message accessible. Do not claim physical exactly-once external chat effects or turn the bridge on. v1 does not wake Herdr panes or install native routines; ordinary agent inbox check-in can discover update notices while retaining PR/CI responsibility.

6. Complete no-clone Compose distribution

A release may omit compose until a disposable Linux smoke test proves a complete bundle. The bundle includes release-specific compose.yaml, non-secret .env.example, setup README, database certificate/init scripts and every local file referenced by Compose. No build: stanza or source checkout dependency. Application and migration use the same immutable dashboard digest; include a published database image containing the pinned pg_textsearch extension, certificate-generation image and optional CLI/Mattermost image digests. Do not advertise missing/unpullable artifacts. Record image platforms and minimum tested Compose version, rather than assume four CLI platforms imply four container platforms. Initial guaranteed container platform is Linux amd64; unsupported engine platforms refuse with instructions. Optional registry authentication is a documented operator precondition; a public artifact is not a promise of anonymous image access. Never embed registry credentials or require maintainer-only farm01 settings.

Operator flow: install CLI through #127 → update compose fetch --version V --dir NEW_DIR → inspect/fill .env using documented secret generation and private permissions → optional explicit registry login → docker compose --project-directory NEW_DIR up -d --wait → check health/meta → register/install skills. Manual download/extract of the verified same bundle is also supported. Optional chat remains a profile; update observation is off until explicitly configured. The updater refuses a populated destination, so it cannot overwrite .env, mounts or an existing deployment. Upgrading an existing installation is a reviewed migration/deployment runbook, not this bootstrap command. Never prune volumes on failure or rollback. A source checkout's developer Compose can remain separate; avoid altering #127's first-install UX while consuming its installed CLI.

Risks / Trade-offs

  • Trusted release compromise → integrity checks do not authenticate a different publisher; explicit origin pins, immutable-release enrollment and no manifest execution reduce the surface. Stronger attestations require a separate proposal.
  • Partial local multi-link update → stage/preflight, per-link journal and guarded recovery; report partial result honestly, retain old bundles.
  • Self-reported installation evidence → label attribution and freshness; no security enforcement or claim disposition depends on it.
  • Provider contention → shared credential budget, six-hour cadence, independent queue/flag; CI observation retains its current gates and proofs.
  • Notification noise/late reports → opt-in only, once per target, daily summary cap, new-report reconciliation; unknown installs receive no notices.
  • False no-clone promise → real bundled support-file validation and clean Linux image-pull/bootstrap proof; no manifest Compose entry until it passes.
  • Updater/schema drift → independent manifest, updater, board API and migration compatibility fields; preserve offline path and explicit operator rollout.

Migration Plan

Ship the four implementation PRs in tasks.md only after a separate apply authorization. PR1 consumes #127's release interfaces; it can add compatible validation/packaging without modifying that proposal. CLI and server work then share its checked schema. Allocate additive schema ordinal against then-current main with coordinator approval; use monotonic schema markers and verify upgrade from an existing board. Default queue/observer off. Enable on a disposable installation, exercise release/report/notice failures, then separately authorize deployment/activation. No captain tag or real release is cut by an implementing worker without explicit permission.

Rollback disables updates queue/cron admission and preserves snapshots/reports/receipts. Compatible prior app images retain the additive schema marker; do not lower it or delete tables/history. CLI/skills recover only to retained verified compatible versions through explicit local action; existing running harnesses are not restarted. Compose rollback belongs to its deployment runbook and retains data volumes and environment files.

Open Questions

None blocking. The three material policy decisions are approved. Exact future migration ordinal and immutable image digests are implementation-time allocation/output values, not design choices; they must be verified before their respective PR or release is published.

Requirements — externally observable behavior

Spec Delta

Purpose

Give operators and agents trustworthy, actionable visibility into CLI and skill drift, with explicit local upgrades and a complete release-pinned Compose bootstrap path that preserves existing work and data.

ADDED Requirements

Requirement: Release-pinned authoritative catalog

The system SHALL consume a supported versioned manifest from the configured GitHub repository's immutable published release. The board SHALL expose only validated cached status and provenance. Stable selection SHALL exclude drafts/prereleases and SHALL NOT silently downgrade an accepted component or reinterpret a published version with changed identity.

Scenario: Published eligible release
  • WHEN complete bounded release enumeration identifies a higher eligible stable SemVer with matching manifest, source and asset identities
  • THEN the catalog records those verified component identities and exact release provenance
Scenario: Missing or changed authority
  • WHEN no eligible release exists, enumeration is incomplete, the release is mutable, or an existing version's digest changes
  • THEN the result identifies unavailability/incompleteness/conflict, retains the last validated snapshot and does not advertise a fresh update

Requirement: Independent artifact identities

The manifest SHALL identify CLI SemVer/build/binary and archive digests, independently versioned skills with archive and canonical installed-tree digests, compatibility requirements and supported platforms. Unchanged skills SHALL retain their identity across CLI releases; changed skill payloads SHALL receive a new version. Hash validation SHALL NOT be described as independent publisher authentication.

Scenario: CLI-only release
  • WHEN a release advances CLI identity while retaining the installed verified skills version/digest
  • THEN the comparison reports the CLI update separately and reports those skills as current
Scenario: Distinct skills hashes
  • WHEN an archive checksum matches but its extracted tree differs from the advertised canonical installed-bundle digest
  • THEN skill installation refuses without changing discovery links

Requirement: Read-only update checks

update check and skills outdated SHALL compare actual local identities and receipts with the selected catalog without installation, enrollment or board mutation. Results SHALL expose per-component state, compatibility, source/freshness and next action in human and versioned JSON output. Update availability SHALL return exit 0; existing error-code conventions SHALL remain intact.

Scenario: Outdated installed component
  • WHEN a read-only check finds a newer compatible component with fresh validated catalog evidence
  • THEN it reports update_available, installed/target identities and explicit next action, exits successfully and changes no binary, skill link, report or notice
Scenario: Unknown, ahead or stale install
  • WHEN an installation lacks provable identity, is newer than the selected target, or catalog evidence is stale/unavailable
  • THEN it reports unknown, ahead or the explicit freshness failure rather than claiming it is current

Requirement: Explicit compatible local updates

Updates SHALL target an exact version and one named component, require controlling-TTY consent or explicit unattended confirmation, and verify provenance/hashes/compatibility before replacing managed content. Declined consent, unsupported platform, incompatible updater/board or downgrade SHALL preserve the original installation. Checks SHALL never imply consent or migrate the board.

Scenario: Unattended refusal
  • WHEN update apply has no controlling TTY and no explicit confirmation
  • THEN it refuses before replacing anything and explains how to confirm the exact operation
Scenario: Compatible CLI update
  • WHEN the approved exact CLI release is compatible and its archive/binary/version are verified against a managed destination and current fingerprint
  • THEN it atomically replaces that destination, records the installed identity and retains verified recovery material without restarting a harness or changing claims
Scenario: Compatibility refusal
  • WHEN the target requires a newer updater, unsupported platform/API range or higher board schema floor
  • THEN apply identifies the unmet requirement and changes no installed component or database schema

Requirement: Managed skill ownership and interruption recovery

Offline embedded skills install SHALL remain available. Remote upgrade SHALL preserve the existing verified bundle/owned-link contract and retain old bundles. Foreign or edited content SHALL cause refusal. Interrupted per-link changes SHALL be recorded truthfully and recovered only after revalidating matching owned destinations; all-directory atomicity SHALL NOT be claimed.

Scenario: Foreign or edited skills
  • WHEN a chosen discovery destination is foreign, an old bundle is edited or a link changes during staging
  • THEN upgrade refuses that overwrite, preserves user content and reports the conflict and any already-committed owned-link changes
Scenario: Interrupted switch
  • WHEN a process stops after some owned links advance
  • THEN recovery can identify their exact prior/new identities, revalidate them and explicitly complete or restore matching links without overwriting intervening manual changes
Scenario: Existing agent session
  • WHEN new skill files have been installed
  • THEN output instructs the agent to re-read the changed workflow and does not claim model context, routines or wake hooks refreshed automatically

Requirement: Bounded trusted download transport

Metadata and downloads SHALL have byte/extraction limits, deadlines, cancellation and bounded retry/redirect handling. Every destination SHALL satisfy configured HTTPS/public-origin rules. Board credentials SHALL never be sent to release hosts; API credentials SHALL NOT follow a cross-host asset redirect. Rate limits SHALL retain provider retry floors within bounded operation time.

Scenario: Malicious archive or redirect
  • WHEN a response exceeds limits, resolves to a private endpoint, redirects outside approved hosts, or an archive contains traversal, links, special files or duplicate paths
  • THEN the operation refuses, preserves original installed content and emits a safe typed error without secret/raw-body output
Scenario: Throttled provider
  • WHEN a 429 or GitHub secondary limit requests a delay beyond the command's deadline
  • THEN the command returns a retry time instead of spinning or silently ignoring the provider floor

Requirement: Durable independent release observation

Board observation SHALL be independently enabled, bounded and durable across replicas/restarts. It SHALL retain last-known-good snapshots on errors, reject stale-worker commits and show fresh/stale/unavailable observation state. Provider outages SHALL NOT block board readiness, CI work or pooled concurrent requests. HTTP SHALL occur outside ownership/budget transactions.

Scenario: Concurrent or crashed observers
  • WHEN two replicas race or an admitted observer dies and a later worker recovers its lease
  • THEN only the current fenced observation can commit; old results cannot overwrite newer state and the board continues serving
Scenario: Observation independent of PR flag
  • WHEN updates are enabled while PR observation is disabled
  • THEN release observation can proceed under its own gate while sharing the configured GitHub credential budget, and no PR queue is unpaused
Scenario: Invalid provider response
  • WHEN fetch is malformed/oversized/unauthorized, or a 304 has no matching validated cached representation
  • THEN error/freshness metadata is recorded, previous valid bytes remain visible and no fresh target or notification is created from the failure

Requirement: Explicit attributed installation reports

Installations SHALL report only through an explicit API operation, with random local installation identity, component identities, channel, report sequence/idempotency key and notification consent. Reports SHALL contain no secrets, host paths or repo inventory. Newer reports SHALL win; identical retries SHALL be idempotent and changed reuse SHALL conflict. Evidence SHALL be labeled self-reported under existing auth policy.

Scenario: Multiple seats for one agent
  • WHEN one agent reports two installations with different versions
  • THEN both installations remain distinguishable without one overwriting the other or exposing workstation paths
Scenario: Delayed or conflicting report
  • WHEN an old sequence arrives after a newer report or the same idempotency key is reused with changed content
  • THEN it cannot replace newer identity/consent and reports stale sequence or conflict
Scenario: Verified principal mismatch
  • WHEN a report's declared agent conflicts with the verified principal under the existing principal-mismatch policy
  • THEN the existing guard applies without #57 weakening it or turning on auth enforcement

Requirement: Opt-in bounded agent signals

Captain summary SHALL show catalog freshness and reported drift. Agent notices SHALL require explicit opt-in, recent installation evidence and a valid compatible target mismatch. Unknown installs SHALL receive no notices. The board SHALL durably deduplicate each recipient/component/target identity across installs, retries and replicas, coalesce pending releases and cap summaries at one per recipient/day.

Scenario: Late report and repeated job
  • WHEN an opted-in recent report arrives after release discovery and multiple reconciliation attempts process it
  • THEN it produces at most one durable inbox notice for that recipient/component/target identity with a concrete check/apply action
Scenario: Unknown or withdrawn installation
  • WHEN no verified report exists, its report is older than seven days, or the recipient turns consent off
  • THEN no new agent notice is sent; unsent withdrawn intents are cancelled and delivered history remains
Scenario: Mattermost outage or disabled bridge
  • WHEN chat routing is disabled or Mattermost is unavailable
  • THEN the committed board notice remains accessible, chat failures do not affect core work, and no bridge or Herdr wake adapter is enabled automatically

Requirement: Honest dashboard status

The dashboard SHALL show available/installed component identities, installation recency, catalog/error time, compatibility and unknown/stale/conflict states with actionable next steps. It SHALL preserve the existing Kanban and theme. The summary SHALL NOT infer that every registered agent reported an installation, that skills were re-read, or that CI responsibilities were discharged.

Scenario: Self-reported stale seat
  • WHEN a seat has an outdated report and fresh target information
  • THEN its row identifies stale self-reported evidence separately from the available release and suggests a check/report, rather than certifying current installation state

Requirement: Complete release-pinned Compose bootstrap

A manifest SHALL advertise Compose only after the complete bundle has passed disposable Linux bootstrap proof. It SHALL include all referenced local support files, secret-free templates, image digests/platforms and registry-access prerequisites, with no build/source dependency. Fetch SHALL stage into a fresh directory only and SHALL NOT start services, modify an existing .env, migrate a live deployment or prune data.
